We need more and fewer HTTP methods

Note: This draft needs technical refinement. It overstates the case severely.

The standard HTTP methods are sometimes fine, but sometimes they're just really awkward, or invoke an idea of what they should be that is just totally wrong.

PUT does not mean "replace the entire resource", even though it kind of feels like it. The semantics are that it is idempotent, and that it sends a payload. Partial updates are completely able to be done with PUT, because partial updates are idempotent.

PATCH similarly doesn't mean "partial update". That's allowed, but PATCH's semantics are that it is NOT idempotent. PATCH allows for a lot more creativity. You can make a custom format that says "increase field xyz by 5". But the method name invokes the idea of a git patch, which feels more similar to a "change line X to this new value" type of operation than an instruction list. It almost feels like a partial update kind of name.

We could lament the names. PUT might be better understood if the name was SET instead. It could invoke the idea of setting a key, so it might be more obvious that a partial update would work.

Or PATCH might be better called MODIFY, where the obvious question would be how and the idea of modifying it with commands would again be more obvious. But I think maybe all of that is the wrong question.

The villain is well-known methods

The big problem is that well-known methods are, in many cases, kind of a bad idea. We should use a lot more flexibility to use custom method names that have their own semantics.

We know what a resource is. It's similar to an object in programming. And we don't limit object method names to a standardized set of names with pre-defined semantics. We'd never even think of doing that, it's so obviously silly.

So why are we doing that with HTTP? It's at least partly because HTML overloaded the method names to encode its form handling, and we haven't broken free from that idea.
